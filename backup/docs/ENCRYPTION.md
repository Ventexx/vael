# Protect

`protect.py` is a standalone file and archive protection tool. Put it beside
`backup.py` to enable optional encrypted backup creation and automatic unlocking
for updates and verification. Neither script requires the other for its basic
standalone functionality.

It uses standard **7z AES-256 encryption with encrypted headers**, implemented by
7-Zip. There is no proprietary container or custom encryption algorithm. A
compatible 7-Zip application and the correct password can recover the files even
without these scripts. See the [official 7z format description](https://www.7-zip.org/7z.html).

## Start here

Install Python and the 7-Zip command-line tool. In the folder containing
`protect.py`, run:

```text
python protect.py
```

The menu offers encrypt, restore, export unencrypted archive, change password,
and verify. If `backup.py` is beside it, create protected backup and update backup
are available too. Configure source folders in `backup.py` before using those two
actions. You can copy `protect.py` alone to another folder and use it independently.

Passwords are entered in a terminal without echo, confirmed when creating new
protection, and retained only for the current operation. New passwords entered
through the interface must contain at least 12 characters; length alone is not a
strength guarantee. Prefer a long, unique password generated by a password
manager. There is **no password reset, master password, or recovery key**.

`python protect.py --generate-password` prints a randomly generated password.
Save it in a password manager; it is intentionally visible in terminal scrollback.
The tool does not save or automatically apply it.

## Commands

Quote paths containing spaces. Output folders must already exist; the final
output file or restore directory must **not** exist. Input files are retained.

| Task | Command |
| --- | --- |
| Protect an existing 7z archive | `python protect.py --encrypt "D:\Backups\Backup.7z" --output "D:\Backups\Private.7z"` |
| Protect any ordinary file | `python protect.py --encrypt "D:\Files\report.pdf" --output "D:\Backups\Private.7z"` |
| Recover files into a new directory | `python protect.py --restore "D:\Backups\Private.7z" --output "D:\Restored"` |
| Create an unencrypted archive copy | `python protect.py --decrypt "D:\Backups\Private.7z" --output "D:\Local\Plain.7z"` |
| Create a copy with a different password | `python protect.py --change-password "D:\Backups\Private.7z" --output "D:\Backups\NewPassword.7z"` |
| Test integrity and protection | `python protect.py --verify "D:\Backups\Private.7z"` |
| Create a new protected backup through the companion | `python protect.py --new-backup --output "D:\Backups\Private.7z"` |
| Update a backup through the companion | `python protect.py --update-backup "D:\Backups\Private.7z"` |

Use `--sevenzip "C:\Program Files\7-Zip\7z.exe"` if detection fails. For archive
conversion, `--work-dir "D:\Private Temp"` chooses an existing scratch directory.
Choose a local, private folder outside cloud synchronization, preferably on an
encrypted disk. `--accept-config-changes` approves changed sources when used with
`--update-backup`; otherwise use the backup menu to review and approve them.
`--history "D:\Private History"` selects the existing history folder for either
companion backup action. Keep using the same location across both scripts.

Existing **7z archives are rebuilt with their contents at the same paths**. A
backup archive's `manifest.json` is preserved, so the resulting copy remains
updatable by `backup.py`. Other inputs, including `.zip` files, are stored as one
file inside the encrypted 7z archive. Restoring such an input gives that original
file back; it does not unpack nested archives automatically.

Changing a password retains the old copy. Check the new copy before deciding what
to do with the old one. Old copies, including cloud version history, still use
their original passwords. Repacking also changes the archive checksum: backup
verification may report **unknown history** until a successful backup update
records the new version. This does not by itself mean corruption. Protect's
verification checks integrity/protection, not backup version history.

## Updating an encrypted backup

Use the same command as an ordinary update:

```text
python backup.py --update "D:\Backups\Private.7z"
```

The backup script recognizes encryption, asks for the password once, and passes
an in-memory password session to the companion. Work happens on an encrypted
transaction copy. The original remains intact until the replacement passes
archive integrity, content-inventory, and encryption checks. The checks reject
readable plaintext headers or nonempty files that lost encryption. Empty files
and directory entries have no content bytes to encrypt; their names are protected
by the encrypted header.

Updated files are added, deleted source files are removed, and changed source
configuration still needs approval. Encryption does not change mirror behavior
or provide automatic older versions. The entire encrypted archive may need to be
uploaded again, depending on the cloud provider.

The backup destination must be outside every configured source folder, so the
archive and its transaction files cannot accidentally become their own inputs.

For a new protected backup, use `backup.py --new --encrypt`. From a terminal,
plain `--new` or menu Create offers protection if the companion exists. The
question happens before creation. Use `--plain` to suppress it. An unattended
plain `--new` remains unencrypted for compatibility with existing jobs.

## Recovery without the scripts

1. Install a compatible 7-Zip application.
2. Open the encrypted `.7z` file.
3. Enter the saved password, then extract to a private local folder.

The password is all the secret material needed. No account, license, local key
file, or connection to this project is required. Extracting files leaves the
original encrypted archive unchanged. Decryption to a new unencrypted `.7z`
through Protect is a separate action; it is not necessary for normal recovery.

## Privacy and temporary data

- Protected file contents, member names, folder names, and the embedded backup
  manifest are encrypted. The outer filename, size, and filesystem timestamps
  remain visible.
- Passwords are passed to 7-Zip through a private standard-input pipe, never
  command-line arguments, environment variables, history files, or logs. The
  scripts do not remember credentials. Python strings cannot guarantee secure
  erasure from memory; this does not defend against a compromised computer.
- New encrypted backups and normal encrypted updates do not extract all files
  into plaintext scratch. They still read your original source files. Small
  manifest and deletion-list scratch files use the system temporary directory.
- Protect's encrypt-existing-archive, password-change, and unencrypted-export
  actions **do extract plaintext temporarily** to rebuild and verify the archive.
  Allow space for roughly two extracted copies, the staged output, and the
  original. The system temp directory is the default and may be redirected by
  your environment; check it or choose `--work-dir` explicitly.
- Restore stages plaintext beside the requested restore destination. That is
  where you asked to receive decrypted files; choose it accordingly.
- Cleanup is attempted on normal completion, failure, and cancellation. A crash,
  power loss, or permission error can leave temporary data. Deleting it is not a
  guarantee of physical secure erasure, especially on SSDs or synced storage.
- Backup history, pending history records, and diagnostic logs are **not
  encrypted** and can reveal source paths. Keep these local. Upload only the
  finished protected archive.

Protecting a file does not delete its original, revoke existing plaintext
uploads, or retroactively encrypt older copies. Store scripts in a trusted local
folder; the companion loader executes the exact neighboring Python file and
checks its interface version, not its authenticity.

## Supported scope and failure behavior

The tool handles regular files and directories. Conversion and restore reject
unsafe paths, case-colliding names, and link/reparse-point entries instead of
extracting them. ACLs, alternate data streams, hard links, and other specialized
filesystem metadata are not promised to round-trip. It is not a system-image or
live-database backup tool.

Conversions always publish a new file and never replace the input. A completed
rebuild is tested, extracted again, and compared by file hashes and directory
names before it is published. Existing outputs are refused. Normal backup
updates instead use the backup app's existing staged replacement and history
recording. Both scripts coordinate using the same archive locks.

Restore validates the temporary extracted tree before moving files into a newly
reserved destination. If final placement fails, the message identifies possible
partial restored files; the encrypted input remains unchanged.

New-file publication uses Windows no-overwrite rename or POSIX hard links. A
POSIX destination filesystem that lacks hard links fails safely; choose a local
supported filesystem and copy the finished archive afterward. Network locking,
arbitrary external writers, and power-loss durability are not guaranteed.

7z encryption provides password-based confidentiality. Integrity tests and local
hash comparisons detect ordinary damage; this tool does not sign archives,
authenticate their sender, or prevent replacement with an older valid backup.
Use a trusted copy of backup history when checking which version you have.

Encrypted commands need a real terminal for hidden password entry. There is no
password command-line option or unattended credential store. `--check` in the
backup app tests the environment, not encryption compatibility. This version's
integration suite was exercised with NanaZip 7.0 (2609.2) on Windows; test your
installed archiver before relying on another build or platform. Protection checks
fail closed if its password/header behavior is incompatible.

Standalone Protect returns 0 on success, 1 on operation/password/cancellation
failure, and 2 for invalid command syntax. Delegated backup operations return
the [backup exit codes](EXIT_CODES.md), including 5/6 when the backup was published
but history needs attention. Read the message before retrying.

## Companion interface

Both scripts advertise `COMPANION_API_VERSION = 1`. Discovery only loads the
expected sibling path, never a similarly named module from the current directory
or Python search path. Missing/incompatible companions produce actionable errors;
plain standalone operation remains available without them.

Backup injects a `PasswordSession` into its archiver runner. The runner delegates
all write, listing, test, rename, delete, and manifest operations through that
session; there is no password-bearing child-script command line. Protect's
backup actions call the backup entry point directly in the same process. Session
references are released at the end of the operation. Keep the two distributed
scripts together and update both when changing this interface.
